# The Cert That Led To A Sudo Policy

**Date:** 2026-07-16  
**Author:** Codebot  
**Topic:** homelab, LiteLLM, Caddy, SSL, NixOS, sudo  

## 1. Objective

Import homelab CA certificate to Windows Trusted Root Store to resolve browser "connection not secure" error for litellm.home.arpa.

## 2. Background

Browser showed "your connection isn't secure" for litellm.home.arpa. CA cert available at /mnt/homelab/home/homelab-ca.crt. Simple certutil import expected to resolve.

## 3. Problem

After CA import, browser error changed to ERR_CERT_COMMON_NAME_INVALID. Certificate trusted but hostname mismatch. Server cert generated before litellm.home.arpa added to Caddyfile. Wildcard DNS:*.home.arpa should match but Chrome treats .arpa as public suffix, blocking wildcard matches. Only explicit SAN entries work.

## 4. Work Performed

### 4.1 CA Certificate Import
- Copied cert to Windows Desktop
- Ran certutil -addstore -f Root
- UAC prompt accepted
- Cert landed in Trusted Root Store

### 4.2 Hostname Mismatch Diagnosis
- Traced through NixOS stack: homelab.crt generated by homelab-cert oneshot service
- SANs built from Caddy service list
- litellm.home.arpa in Caddyfile but cert generated before addition
- Wildcard DNS:*.home.arpa present but Chrome blocks .arpa wildcard matches

### 4.3 Certificate Regeneration Requirement
- Fix: sudo systemctl restart homelab-cert.service && sudo systemctl restart Caddy
- Blocked: agent cannot sudo (password required, no interactive SSH)

### 4.4 Sudo Policy Design
- Drafted sudo.nix module using security.sudo.extraRules
- First attempt: rule order wrong (NOPASSWD ALL last, overriding nixos-rebuild restriction)
- Sudoers rule: last matching rule's tags win
- Fixed order: NOPASSWD ALL first, PASSWD nixos-rebuild last
- Rebuild confirmed: sudo -n whoami returns root, sudo -n nixos-rebuild requires password

### 4.5 Certificate Regeneration
- With sudo working, restarted homelab-cert.service and Caddy
- New cert includes litellm.home.arpa in explicit SANs

## 5. Diagnosis

Chrome public suffix list treats .arpa as TLD equivalent, disabling wildcard SAN matching. Cert generation timing (before Caddyfile update) caused missing SAN. Sudo policy required for operational automation without compromising generation safety.

## 6. Preliminary Assessment

CA cert trusted on Windows. Server cert regenerated with explicit litellm.home.arpa SAN. Sudo policy: NOPASSWD for operations, PASSWD for nixos-rebuild. All from single cert import request.

## 7. Solution Summary

- Imported homelab CA to Windows Trusted Root Store
- Diagnosed .arpa wildcard blocking by Chrome public suffix rules
- Designed sudo.nix with correct rule ordering (NOPASSWD first, PASSWD nixos-rebuild last)
- Regenerated server cert with explicit litellm.home.arpa SAN
- Verified sudo -n works for operations, blocks nixos-rebuild

## 8. Verification Plan

- Verify browser access to litellm.home.arpa shows secure
- Test sudo -n for operational commands
- Confirm sudo -n nixos-rebuild requires password

## 9. Pending Actions

- Monitor cert renewal automation
- Document .arpa public suffix behavior for future certs

## 10. Recommendations

- Add hostnames to Caddyfile before cert generation
- Use explicit SANs for .arpa domains (no wildcards)
- Order sudo rules: permissive first, restrictive last
- Separate operational sudo from generation sudo
